## (c) CPU 参照実装 — 完了(合成重みでの検証)

- `include/strata/nemotron/reference.hpp`、`src/nemotron/reference.cpp`(ライブラリ `strata_nemotron_ref`、GPU も ggml も不要)。
  fp32、1 トークンずつ。llama.cpp(pin 3cf03257)の `src/models/nemotron-h.cpp`、`nemotron-h-moe.cpp`、`mamba-base.cpp` と ggml-cpu の
  `ssm_conv` / `ssm_scan` を読んで写した。コードを読んで確定した要点:
  - 全ブロックが `attn_norm` の RMSNorm を前段に持つ(MoE ブロックも)。
  - Attention は **RoPE なし(NoPE)**、q/k の正規化なし、スケール 1/√128、GQA 32:2。
  - Mamba2: `ssm_in` の出力は z / xBC / dt の順。xBC に因果 depthwise 畳み込み + バイアス + SiLU。dt' = softplus(dt + bias)(閾値 20)、
    s ← s·exp(dt'·A) + B·(x·dt')、y = s·C + D·x、y *= silu(z)、幅 1024 × 8 グループの RMSNorm、`ssm_out`。グループは g = h / (H/G)。
  - MoE: ルータは 4096 次元の入力から sigmoid。選択だけ `exp_probs_b` を足し、重みはバイアス無しの確率を正規化して ×5。expert は
    `latent_down` 後の 1024 次元で relu²(ゲート無し)、`latent_up` で戻す。共有 expert は 4096 次元で relu²。
  - MTP: 種は本体の `output_norm` 後の隠れ状態。`eh_proj [enorm(emb), hnorm(h)]` → Attention(NoPE)→ `post_attention_norm` → MoE →
    **LayerNorm**(RMSNorm ではない)の `shared_head_norm` → 本体の `output`。
- 検証(2026-11-10、この PC、`nemotron_reference_test`、16 項目 ok):
  - Mamba2 の逐次スキャン vs 系列全体の二次形式(SSD の双対形、畳み込みはゼロ詰めの全系列で別実装): 24 トークンで最大差 7.2e-7
    (出力の大きさ 3.4)。CUDA のチャンク型 prefill の正解としても使う。
  - Attention の逐次 KV vs 因果マスク付き一括計算: 最大差 1.8e-7。KV ヘッド 1 がクエリヘッド 2, 3 だけに効くこと。
  - MoE: 選択バイアスは選ぶだけで重みに入らないこと、重みの正規化と ×scale、潜在入力ゼロで relu² の共有 expert だけが残ること。
  - モデル全体: 9 トークン後の状態のコピーから続けて、一括実行とビット一致。MTP 2 段の連鎖が決定的。
- **限界(正直に)**: これは「自分が読み取った llama.cpp の式」に対する自己一貫性の検証。実モデルで llama.cpp と出力が一致するかは
  未検証(実モデルの重みが必要。fp32 にすると 480 GB 級なので、実モデルとの照合は (d) 以降のエンジン本体と llama.cpp のロジット比較で
  行う。ユーザー依頼リストに追加)。

  上書きしたあと A のチェックポイントから再開すると、B の K / V を読んでいた。セルが持つトークン(`kv_tokens`)を記録し、チェック

- **パーキング**: 長い会話(既定 1,024 トークン以上)を別の会話が上書きする前に、状態と K / V(1 トークン約 9 KiB)を RAM へ(既定 8 GiB まで)。
  合成モデルで、B を挟まずに読んだ場合とロジットがビット一致。実モデル: 1,517 トークンの A → B → A の続きで 1,547 トークン中 1,527 を再利用、
  prompt 12.5 s → 1.7 s。退避 140 ms(178 MiB)、復元 46 ms。
- **チェックポイントの位置**: 最後の `<|im_start|>`、長い system prompt の終わり(2 つ目の `<|im_start|>`、1,024 トークン以上で永続)、16,384 トークンごと。最大 6 個。
- **セッションファイル**: `SAVE <path>` / `RESTORE <path>`(サーバーの `/slots/0?action=save|restore`)。合成モデルで、別の会話を挟んで復元した
  続きが中断なしと同じトークン、新しいトークンだけを読む(`test_session_file_save_and_restore`)。

分布の正しさ: 合成モデルで、下書きありとなしの 2 / 3 トークン目の分布の差(全変動距離)が、なし同士の差(サンプリングの揺らぎ)と同じ
大きさ(0.220 対 0.227、0.651 対 0.675、各 1500 回)。`tests/nemotron/test_proto.py::test_sampled_drafts_keep_the_distribution`。

prompt(同じ条件): 3,218 トークン 157.6 tok/s(借用後も同じ)、721 トークン 81.9 tok/s(以前 86〜94: 借りた行を戻すコピー)、

## PCIe のコピーと VRAM の expert の計算を重ねる(2026-11-13、同じ依頼、各 3 回の 2・3 回目)

  だけイベントを待つ。中間の行を「スロットの分 → コピーした分」の順に詰めたので、各エントリの計算は以前と同じ(結果も同じ)。
  `STRATA_NEMO_COPY_OVERLAP=0` で以前の順番に戻る。
- GPU 1 の「expert + コピー」は窓 1 回で 60.7 ms(25.9 + 34.8)から 55 ms 前後。コピー(約 35 ms)のほうが VRAM の expert の
  計算(約 26 ms)より長く、GPU 1 はリンクを待つ。窓 + 下書きは 242 / 210 ms と 234 / 214 ms(重ねる / 重ねない)で、
  回ごとの揺れの中。
- いまの律速: GPU 0 は CPU(窓 1 回 45 ms 空き)、GPU 1 は PCIe のリンク(35 ms)。CPU は窓 1 回で約 147 ms(expert 134 + 下書き 13)

## 長い会話で decode が遅くなる原因(同じ PC、192K の設定、会話の長さ 144K トークン)

  (約 5〜7 ms)。増えたのは MoE 層の前の GPU の待ち(密な処理)で、CPU の expert の時間は増えていない。
- decode のアテンションのカーネルだけを測った(`build/nemotron-run/attn_bench.cu`、GPU 1、Hq 32 / Hk 2 / D 128、エンジンと同じ分割数):

  | セル数 | 1 行(下書き) | 7 行(検証窓) |
  |---|---|---|
  | 4,096 | 1.0 ms | 1.9 ms |
  | 32,768 | 1.9 ms | 11.1 ms |
  | 131,072 | 7.0 ms | 42.5 ms |
  | 147,456 | 7.0 ms | 47.8 ms |
  | 196,608 | 9.6 ms | 64.0 ms |

  1 層あたり。K / V の読み出しは約 22 GB/s で、カードのメモリ帯域(約 450 GB/s)の 5% ほど。窓の各行が K / V を別々に読み、
  K の内積も 1 スレッドが 1 セルを 2 バイトずつ読む。

  `--mtp-slots 64` がない。

## decode のアテンションの書き直し(同じ PC)

- `k_attn_win`(src/nemotron/kernels.cu): 1 ブロックが KV ヘッド 1 つ、1,024 セルの固定の範囲、窓の 64 個のクエリ(4 行 × 16 ヘッド)を
  受け持ち、K / V の 64 セルのタイルを共有メモリに 1 回読んで全行で使う。範囲とタイルの境目は絶対位置で決め、各行は自分の最後の
  セルで止まるので、行の計算は窓の長さによらず、1 行だけのときと同じ。prompt の経路(テンソルコア、分割なし)は変えていない。
  `STRATA_NEMO_ATTN_WIN=0` で以前のカーネル。
- カーネルだけ(`build/nemotron-run/attn_bench.cu`、GPU 1、1 層あたり):

  | セル数 | 1 行 旧 → 新 | 7 行 旧 → 新 |
  |---|---|---|
  | 4,096 | 1.02 → 0.22 ms | 1.90 → 0.27 ms |
  | 32,768 | 1.93 → 0.45 ms | 11.3 → 1.08 ms |
  | 131,072 | 7.10 → 1.81 ms | 42.9 → 4.06 ms |
  | 147,456 | 7.06 → 1.83 ms | 48.3 → 4.39 ms |
  | 196,608 | 9.67 → 2.67 ms | 64.0 → 6.01 ms |

  窓の各行は 1 行だけで計算したものとビット単位で同じ(全セル数)。旧カーネルとの差は最大 1.2e-6(多くは 0)。
- テスト: nemotron_kernels_parity、nemotron_engine_parity(MTP あり / なしで同じ greedy トークン)、借用モード、CPU expert、
  protocol 13 件、すべて通過。
- 実モデル、72K トークンの会話(docs の文書 + 要約の依頼、思考なし、温度 1.0、128K の設定、`--mtp-slots 64`、2 回目は prompt を再利用):

  | | 検証窓 1 回 | 下書き 1 回 | 生成 |
  |---|---|---|---|
  | 旧 | 425 / 383 ms | 8.64 / 8.39 ms | 8.3 / 9.3 tok/s |
  | 新 | 259 / 215 ms | 6.02 / 5.67 ms | 12.7 / 15.4 tok/s |

  144K の会話は測っていない(カーネルの数字からは、窓 1 回で約 350 ms 減る計算)。

## 2 GPU の prompt の流れ作業(同じ PC)

- 今までは 1 つのチャンクが GPU 0 の層 → GPU 1 の層と進み、終わってから次のチャンクだった(どの時点でも動く GPU は 1 枚)。
- `feed_piped`(src/nemotron/engine.cu): GPU ごとにホストのスレッドを 1 本持ち、GPU 1 がチャンク k を読む間に GPU 0 がチャンク k+1 を
  読む。チャンクの行は GPU 0 からホストの受け渡しバッファ(pinned、1 チャンク分の 64 MiB)を通って GPU 1 へ。VRAM は使わない
  (スロットの数は変わらない: 206 / 171)。
- MoE のホスト側のバッファ(ルーティング、CPU の expert の出力など)は GPU ごとに持つ(2 枚目の分 369 MiB、合わせて 433 MiB の pinned)。
  CPU の expert のプールは 1 度に 1 つのチャンクの層(mutex)。カウンタは呼び出しごとに足してからまとめて加える。
- 流れ作業にするのは、チェックポイントまでの、8 行を超えるチャンクの並び(2 つ以上)。チェックポイントでは両方の GPU が揃う。
  途中で止められたとき(STOP)、GPU 0 が先のチャンクまで読んでいたら、その会話の状態は捨てる(次はチェックポイントから)。
- 各 GPU は自分のチャンクを順番に、1 枚ずつのときと同じ計算で読む。テスト(2 GPU、チャンク 16 と 9、MTP あり / なし)で prompt の
  ロジットと greedy トークンがビット単位で同じ。`--no-prefill-pipe` / `STRATA_NEMO_PIPE=0` で以前の動き。
- 実モデル、36,529 トークンの prompt(docs の文書 + 要約の依頼、128K の設定、`--mtp-slots 64`、各 1 回):

  | | prompt |
  |---|---|
  | 1 チャンクずつ | 204.2 s(178.9 tok/s) |
  | 流れ作業 | 152.9 s(238.9 tok/s、+34%) |

  2 倍にならないのは、CPU の expert と RAM の帯域を 2 枚で分け合うため(内訳は測っていない)。

## prompt の CPU expert の結果は CPU が計算した行だけ GPU へ(同じ PC)

- 以前は MoE 層ごとに、CPU の expert の出力バッファを全行(4,096 行のチャンクで 4,096 × 22 × 1,024 float = 369 MB)GPU に送っていた。
  GPU 0 のリンク(3.1 GB/s)では 1 層 120 ms ほどになる計算。merge_rows が読むのは CPU が計算した行だけなので、その行だけを送る
  (CPU の expert ごとに並びの 1 区間、隣り合う区間は 1 回のコピー)。`STRATA_NEMO_CPU_ROWS_ALL=1` で以前の動き。
- 小さなモデル(300 トークン、チャンク 64、CPU に送る expert あり)で、以前と greedy トークンが同じ。テストはすべて通過。
- 実モデル、同じ 36,529 トークンの prompt(流れ作業あり、各 1 回):

  | | prompt |
  |---|---|
  | 全行を送る | 154.0 s(237.2 tok/s) |
  | CPU の行だけ | 132.2 s(276.3 tok/s、+16%) |

  この日の始め(1 チャンクずつ、全行)の 178.9 tok/s からは +54%。

## 残っていること(2026-11-14)

上の B・C・E(調べて採らなかった)・流れ作業・アテンション・CPU の行の転送は済み。残り:

- 速さ: decode は CPU の expert(RAM の帯域)と GPU 1 の PCIe が律速。窓の中の同じ expert を GPU が 1 回だけ読む案は数 ms の見込みで未着手。
- 機能: バッチのスロット(複数リクエストの同時生成)、logprobs と logit_bias、ビルド済みエンジンの配布、アプリからの起動。
- 確認: llama.cpp とのロジットの照合(下のリストの 5)、128K いっぱいの prompt、sm_120 以外の GPU、Linux、小さい PC。

## 実装しなかったもの(理由)

- バッチのスロット(複数リクエストの同時生成): Mamba の状態と K / V をリクエストごとに持ち、decode のカーネルを複数行にする必要がある。
  1 件ずつの速さを先にした。
- CUDA graph: どの expert を GPU と CPU に分けるかを層ごとにホストが決めるので、グラフにできるのは Mamba のブロック 1 つ程度。
  起動の回数はまとめたカーネル(層あたり 2n+2 → 5)で減らした。

## 既知の性能上の限界(未測定のものを含む)

- 128K いっぱいの prompt は未測定(30K で 192 tok/s)。
- `Engine` のデストラクタが GPU メモリを解放しない(プロセス終了で解放。サーバーの使い方では問題にならない)。
- logprobs と logit_bias は未対応(`ERR ... not available on this engine path yet`)。
- ビルド済みのエンジンは配布していない(ソースからビルド)。アプリの同梱エンジンでは動かない。
